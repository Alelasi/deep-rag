章节大纲

1为什么需要 Agentic RAG？~800字

1.1 传统 RAG 的三大痛点

  • 只能查本地知识库，无法回答实时问题（"最新版本有什么bug？"）
  • 没有质量校验，答案可能包含幻觉
  • 检索失败时无降级策略，直接返回"不知道"

1.2 Agentic RAG 的核心差异

  • 动态工具路由：Agent 自动选择向量检索 / GitHub API / Web 搜索
  • 自纠错循环：Corrective RAG（输入端）+ Self-RAG（输出端）
  • 多工具编排：并行调用 + 结果聚合 + 质量评估

1.3 真实场景示例

  • 对比传统 RAG vs Agentic RAG 处理"LangChain 0.3 新特性 + 已知 bug"的过程
  • 展示工具路由决策链和最终综合答案

写作要点：不要上来就讲架构，先让读者感受到痛点是真实的。用学习 LangChain 时文档分散的个人经历引入。

2架构设计：7层 Pipeline 状态机~1500字

2.1 为什么用 LangGraph 不用 LangChain

  • LangChain Chain 是线性的，做不了循环和条件路由
  • LangGraph 支持状态持久化、条件边、循环
  • Checkpoint 机制可做对话中断恢复

2.2 7层 Pipeline 详解

层节点核心逻辑关键代码
1Query Analysis意图识别 + 问题分类src/agents/analyzer.py
2RetrievalBM25 + Vector + RRF 融合src/retrieval/hybrid.py
3Doc GradingLLM/规则判断文档相关性src/agents/grader.py
4Generation带上下文 + 引用标注的生成src/agents/generator.py
5Fact Checking幻觉检测：答案 vs 上下文一致性src/agents/fact_checker.py
6Conflict Detection多文档矛盾检测与处理src/agents/conflict_resolver.py
7Final Answer格式化输出 + 来源标注src/graph.py

2.3 两个纠错循环

  • Corrective RAG：第3层 → 不相关 → Query Rewrite → 回到第2层（最多3次）
  • Self-RAG：第5层 → 检测到幻觉 → Regenerate → 回到第4层（最多1次）
  • 代码实现：graph.add_conditional_edges() 条件路由

3关键技术决策与取舍~2000字

3.1 混合检索：为什么不用纯向量？

  • 纯向量 Top-5 准确率 78%，加 BM25 后 88%（+10pp）
  • RRF 融合公式：score(d) = Σ 1/(k + rank_i(d))，k=60
  • 为什么不直接用原始得分：不同检索器分值尺度不可比
  • 代码：HybridRetriever.retrieve() 并行调用 + RRF 排序

3.2 Self-RAG：默认关闭的工程取舍

  • 每次事实校验额外 5-7 秒（7B 模型）
  • fast 模式（默认）：校验后直接输出，省 5-7s
  • 质量模式：校验失败可 regenerate，适合高难度场景
  • 面试场景：如何向面试官解释"默认关闭"不是偷懒，而是延迟优化的工程决策

3.3 Reranker：从 CPU 到 API 到关闭

  • Cross-Encoder CPU 模式：准确率 +7pp，但延迟从 5s 飙到 24s
  • SiliconCloud API 模式：~200ms，但需要 API Key
  • 7B 模型 VRAM 紧张时必须关闭 Reranker（4.6+0.5+0.5+1.2=6.8GB > 8GB）
  • 最终方案：API 模式默认开，无 Key 时降级 CPU，VRAM 不足时关闭

3.4 多向量数据库：抽象接口设计

  • AbstractIndexer 统一接口：retrieve / add / delete / count
  • 5 种实现：ChromaDB / Qdrant / FAISS / LanceDB / pgvector
  • 切换只需改 VECTOR_DB 环境变量
  • 分层存储方案：FAISS 热缓存 → LanceDB 核心库 → 冷存储

写作要点：每个决策都讲"为什么这么选"和"放弃了什么"，不要只讲最终方案。读者最想看的是取舍过程。

5工程化实践：从玩具到生产~1500字

5.1 CI/CD 流水线

  • GitHub Actions：test×3（Python 3.11/3.12/3.13）+ lint + security + docker
  • concurrency 控制取消旧 run，避免排队
  • conftest.py 自动跳过依赖外部服务的测试
  • Dependabot 自动更新（limit=3 避免CI资源耗尽）

5.2 Docker 多阶段构建

  • Builder + Runtime 两阶段，减小镜像体积
  • 非 root 用户（appuser）运行，安全合规
  • HEALTHCHECK + 精简 COPY（不复制 tests/docs）
  • 移除 Reranker 依赖，构建时间从 19min 降到可控范围

6踩坑与经验~1200字

6.1 ChromaDB HNSW 索引损坏（6次）

  • 根因：在已有数据库路径上创建 PersistentClient 会导致 HNSW 大规模损坏
  • 解决：服务器模式 + HttpClient，禁止 PersistentClient
  • 教训：社区文档不一定对，要看官方源码

6.2 7B 模型 + Reranker 显存溢出

  • RTX 4060 8GB：模型 4.6GB + Embedding 0.5GB + ChromaDB 0.5GB + Reranker 1.2GB = 6.8GB
  • 看似没超，但实际运行时 Reranker 导致模型互相驱逐
  • 延迟从 5s 飙到 41-55s（模型被卸载后重新加载）
  • 解决：ENABLE_RERANKER=false 或用 API 模式

6.3 CI 排队 10 小时未执行

  • 根因：多个 CI run 排队，无并发控制
  • 解决：concurrency.cancel-in-progress: true

6.4 ENABLE_RERANKER 配置未生效

  • 根因：config.py 定义了开关，但 graph.py 两处检索代码从未检查，始终创建 Reranker
  • 修复后 7B 模型延迟从 24.4s 降到 5.7s
  • 教训：配置项必须有测试覆盖验证其生效

写作要点：踩坑章节是最受欢迎的。每个坑讲"现象 → 根因 → 解决方案 → 教训"，不要只讲解决方案。
