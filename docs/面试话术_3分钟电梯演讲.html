一、3分钟电梯演讲

0:00-0:30 项目是什么
我做了一个基于 LangGraph 的 Agentic RAG 系统，叫 DeepRAG。它不是简单的"文档问答机器人"，而是一个带自纠错能力的智能检索系统——当检索到的文档不相关时，它会自动改写查询重试；当生成的答案有幻觉风险时，它会自我反思并重新生成。整个系统是 7 层 Pipeline，7个月从 60% 准确率迭代到现在的水平。
0:30-1:30 解决什么问题
出发点很实际：学习 LangChain/LangGraph 时，官方文档分散在 Python 文档、JS 文档、API Reference、GitHub 四五个地方，版本从 0.1 到 0.3 快速迭代。查一个问题平均要花 10-30 分钟，打开一堆标签页对比版本差异。我就想，能不能用 RAG 自己解决这个问题？

但传统 RAG 有两个硬伤：一是只能查本地知识库，遇到"最新版本有什么bug"这种实时问题就废了；二是没有质量校验，答案可能包含幻觉。所以我把系统做成了 Agentic RAG——Agent 能自动判断问题类型，选择向量检索、GitHub API、Web 搜索等不同工具；生成答案后还有事实校验和幻觉检测。
1:30-2:30 技术方案
核心架构是 LangGraph 状态机驱动的 7 层 Pipeline：
Query Analysis → Retrieval → Doc Grading → Generation → Fact Checking → Conflict Detection → Final Answer

关键技术决策：
- Corrective RAG：文档评分不相关时改写查询重试，最多 3 次
- Self-RAG：生成后做事实校验，检测幻觉并重新生成（默认 fast 模式关闭循环，质量模式开启）
- 混合检索：BM25 关键词 + 向量语义 + RRF 融合排序，Top-5 准确率从 78% 提到 88%
- 多后端支持：ChromaDB、Qdrant、FAISS、LanceDB、pgvector 五种向量库
- 工程化：CI/CD 6 个 job 全通过、Docker 多阶段构建、Railway 部署、GitHub Pages 展示
2:30-3:00 成果与诚实口径
代码量 17,800+ 行，60+ 源文件，17 个测试文件。评测方面，主 Golden 集 60 条，意图专项 150 条 L1≈72%。需要说明的是，这些是离线启发式评测，不是官方 RAGAS 包，也不是生产 SLA。幻觉检测准确率 92%，自动纠错成功率 82%。整个项目已上线 GitHub，有完整的 CI 流水线和在线展示页。

二、技术亮点详述

1. 7层 LangGraph Pipeline

不是简单的 retrieve-generate，而是带两个纠错循环的完整状态机：

层节点作用
1Query Analysis查询分析：意图识别、问题分类
2Retrieval混合检索：BM25 + Vector + RRF
3Doc Grading文档评分：LLM/规则判断相关性
4Generation答案生成：带上下文的 LLM 生成
5Fact Checking事实校验：检测幻觉
6Conflict Detection冲突检测：多文档矛盾处理
7Final Answer最终输出：格式化 + 引用标注

纠错路径：第3层不相关 → Query Rewrite → 回到第2层（Corrective RAG，最多3次）；第5层检测到幻觉 → Regenerate → 回到第4层（Self-RAG，最多1次）

2. Corrective RAG vs Self-RAG

两者解决什么不同问题？
Corrective RAG：解决"检索不到好文档"的问题。当文档评分不相关时，自动改写查询重试，或者用 Web 搜索兜底。这是输入端的纠错。
Self-RAG：解决"生成的内容有幻觉"的问题。生成后检查答案是否包含检索上下文中没有的信息，检测到幻觉则重新生成。这是输出端的纠错。
两者形成闭环：输入端确保文档质量，输出端确保答案质量。

3. 混合检索 + RRF

单一检索方式各有盲区：

方式优势劣势Top-5准确率
纯向量语义理解关键词精确匹配差78%
BM25关键词精确无语义理解~70%
混合+RRF两者优势延迟稍高88%
混合+Reranker精排优化Cross-Encoder慢92%

RRF（Reciprocal Rank Fusion）公式：score = Σ 1/(k + rank_i)，k=60

四、常见面试问题 Q&A

Q1: 为什么选 LangGraph 不用 LangChain？
LangChain 的 Chain 是线性的，做 RAG 可以但做不了复杂的状态机。LangGraph 支持条件路由、循环、状态持久化，才能实现 Corrective RAG 的"不相关就重试"循环和 Self-RAG 的"有幻觉就重新生成"循环。另外 LangGraph 的 checkpoint 机制可以做对话中断恢复。
Q2: Self-RAG 和 Corrective RAG 有什么区别？
Corrective RAG 是输入端纠错：文档评分不相关 → 改写查询 → 重新检索（最多3次）。解决"检索不到好文档"的问题。
Self-RAG 是输出端纠错：生成答案 → 事实校验 → 检测幻觉 → 重新生成（最多1次）。解决"答案包含虚构信息"的问题。
两者形成输入+输出的双重质量保障闭环。
Q3: 混合检索的 RRF 怎么实现的？
BM25 和向量检索分别返回各自的 Top-K 结果，每条结果的得分用 RRF 公式融合：score(d) = Σ 1/(k + rank_i(d))，k=60。这样不依赖原始得分尺度，只看排名，避免了不同检索器分值不可比的问题。融合后再可选 Cross-Encoder Reranker 精排到 Top-5。
Q4: 怎么评价 RAG 系统的质量？
我用了四个维度：
- Context Recall：检索的文档是否覆盖了答案需要的信息
- Context Precision：检索的文档中有多少是真正相关的
- Faithfulness：答案是否忠实于检索到的上下文（不幻觉）
- Answer Relevancy：答案是否回应了用户的问题
诚实说，我用的是离线启发式评估（中文 jieba/bigram 分词），不是官方 RAGAS 包。官方 RAGAS 对中文支持不好，Answer Relevancy 在英文 split 下对中文完全失效。
Q5: 项目有什么不足？
三个主要不足：
1. 评测规模小：Golden 集只有 60 条，意图集 150 条，离工业级评测（几千条）还有距离
2. Self-RAG 默认关闭：因为每次校验要额外 5-7 秒，7B 模型延迟太高。质量模式才开启
3. 知识库规模有限：演示用 LangChain 文档，没有大规模真实场景验证
这些我在 README 的"审计真相表"里都诚实标注了。
Q6: 为什么支持 5 种向量数据库？是不是过度设计？
不是为了炫技，是不同场景的需求：
- ChromaDB：本地开发，零配置启动
- Qdrant：生产部署，支持稠密+稀疏向量混合检索
- FAISS：热数据缓存，查询极快（1.7M docs/s 写入）
- LanceDB：冷数据存储，磁盘友好
- pgvector：已有 PostgreSQL 的团队无缝集成
实际项目中通过统一接口 AbstractIndexer 抽象，切换只需改一个环境变量。
