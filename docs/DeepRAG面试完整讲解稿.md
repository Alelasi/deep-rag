### 核心模块详解

#### 1. 增强检索模块（enhanced_retriever.py）

```python
# 核心流程
def enhanced_retrieve(query: str) -> List[Document]:
    # Step 1: 问题拒识（4层过滤）
    if not is_valid_query(query):  # 长度+恶意+闲聊
        return []

    # Step 2: 多路并行检索
    semantic_results = vector_search(query)      # 语义检索
    keyword_results = bm25_search(query)         # 关键词检索
    hybrid_results = hybrid_search(query)        # 混合检索

    # Step 3: RRF融合（Reciprocal Rank Fusion）
    fused_results = rrf_fusion([semantic_results, keyword_results, hybrid_results])

    # Step 4: ColBERT重排序
    reranked_results = colbert_rerank(query, fused_results)

    return reranked_results[:5]  # Top-5
```

**面试话术**：
> "多路检索的核心思想是'不把鸡蛋放在一个篮子里'。语义检索擅长理解意图，关键词检索擅长精确匹配，混合检索是两者的平衡。RRF融合公式是 1/(k+rank)，k取60，把三路结果统一排序。最后用ColBERT做精细化重排，因为ColBERT是token级别的交互，比简单的向量相似度更准确。"

---

#### 2. Self-RAG 幻觉检测（hallucination_aware_retriever.py）

```python
# 幻觉检测流程
def detect_hallucination(answer: str, context: List[str]) -> float:
    # Step 1: 把答案拆分成独立的claim
    claims = split_into_claims(answer)

    # Step 2: 判断每个claim是否有检索文档支持
    supported_claims = 0
    for claim in claims:
        if is_supported_by_context(claim, context):
            supported_claims += 1

    # Step 3: 计算支持率
    support_rate = supported_claims / len(claims)

    # Step 4: 判定幻觉（阈值0.3）
    if support_rate < 0.3:
        return "hallucination"
    return "faithful"
```

**面试话术**：
> "Self-RAG的核心思想是'让LLM自己反思'。传统RAG直接输出答案，可能包含幻觉。我的做法是：先让LLM生成答案，再让LLM判断每个claim是否有检索文档支持。如果支持率低于30%，就认为是幻觉，触发重新生成。这个机制把幻觉率从20%降到了5%。"

### Q2：RAG的基本流程是什么？

**回答**：
> "RAG的全称是Retrieval-Augmented Generation，检索增强生成。基本流程是：
> 1. **索引阶段**：把文档切块（chunk_size=800），用Embedding模型转成向量，存入向量数据库
> 2. **检索阶段**：用户问题转成向量，用余弦相似度找到最相关的文档块
> 3. **生成阶段**：把检索结果和问题一起发给LLM，生成答案
>
> 我的项目在这个基础上做了很多增强：多路并行检索、RRF融合、ColBERT重排、Self-RAG幻觉检测。"

---

### Q3：为什么选择这些技术栈？

**回答**：
> "选择LangGraph是因为它支持状态机驱动的多Agent协作，比简单的Chain更灵活。ChromaDB是因为它开源免费，支持服务器模式，适合快速开发。LanceDB是因为它性能更好，60倍速度提升，用于实验对比。Redis用于缓存，减少重复查询。LangFuse用于可观测性，RAGAS用于自动化评估。"

---

### Q4：chunk_size为什么选800？

**回答**：
> "这是实验得出的最优值。我测试了200、500、800、1200、1500五个值：
> - 200：太短，上下文断裂，准确率下降10%
> - 500：还行，但复杂问题覆盖不全
> - 800：最佳平衡，准确率最高
> - 1200：开始出现冗余，准确率略降
> - 1500：太长，噪声增多，速度变慢
>
> chunk_overlap设为200，是25%重叠率，确保上下文连续性。"

---

### Q5：ColBERT重排是怎么做的？

**回答**：
> "ColBERT是Contextualized Late Interaction over BERT的缩写。它和传统向量检索的区别是：
> - 传统向量：把整个文档压缩成一个向量，丢失细节
> - ColBERT：保留token级别的向量，做细粒度交互
>
> 具体做法：
> 1. 把query和document都转成token级别的向量序列
> 2. 计算每个query token和所有document token的最大相似度
> 3. 把这些最大相似度求和，得到最终分数
>
> 这样做的好处是能捕捉更细粒度的语义匹配，准确率从88%提升到95%。"

---

### Q6：RRF融合公式是什么？

**回答**：
> "RRF是Reciprocal Rank Fusion，公式是：
>
> score = Σ 1/(k + rank_i)
>
> 其中k是常数（我取60），rank_i是文档在第i路检索中的排名。
>
> 举个例子：文档A在语义检索排第2，关键词检索排第5，混合检索排第3：
> score = 1/(60+2) + 1/(60+5) + 1/(60+3) = 0.016 + 0.015 + 0.016 = 0.047
>
> RRF的好处是不需要归一化，不同检索器的结果可以直接融合。"

---

### Q7：Self-RAG和传统RAG有什么区别？

**回答**：
> "传统RAG的流程是：检索→生成→输出，直接把答案给用户，可能包含幻觉。
>
> Self-RAG多了两个步骤：
> 1. **反思**：生成答案后，判断每个claim是否有检索文档支持
> 2. **修正**：如果检测到幻觉，触发重新生成
>
> 具体实现：
> - 把答案拆分成独立的claim（一句话一个claim）
> - 对每个claim，判断是否被检索文档支持（RAGAS Faithfulness）
> - 如果支持率<30%，认为是幻觉，重新生成
>
> 这个机制把幻觉率从20%降到5%。"

---

### Q8：你的项目和企业级RAG有什么差距？

**回答**：
> "主要差距在三个方面：
> 1. **规模**：我的评估集是150条，企业级可能是10万+
> 2. **多模态**：我只处理文本，企业级可能需要图片、表格、PDF
> 3. **分布式**：我单机部署，企业级需要分布式向量数据库（如Milvus集群）
>
> 但在技术深度上，我的项目覆盖了RAG的核心链路：检索→重排→生成→评估→优化，这是企业级RAG的缩影。"

---

### Q9：你遇到的最大技术挑战是什么？

**回答**：
> "最大挑战是ChromaDB的HNSW索引损坏问题，我遇到了6次。
>
> 根因是ChromaDB的PersistentClient在初始化时会启动compactor线程，如果在已有数据库上创建新实例，会损坏索引。
>
> 解决方案是采用服务器模式+HttpClient：先在空数据库上启动chroma run服务器，所有代码通过HttpClient连接，服务器永不重启。
>
> 这个经历让我深刻理解了'状态管理'的重要性，也让我学会了查阅源码定位问题。"
